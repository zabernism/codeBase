### 2.3 发现的问题

#### ✅ P0-1 硬错误：Chinchilla 公式常数写错

**位置**：第 2 章第 43 题 `Scaling Laws`，源文件 L2973

**原文**：
```
N_opt ≈ 20 × C^0.5, D_opt ≈ 20 × C^0.5
```

**问题**：Chinchilla 论文里的「20」是 **D/N 的 token 配比（每参数 20 token）**，不是幂律系数。把它当成 `20 × C^0.5` 的乘法因子，量纲完全错了。

**验证**：代 C = 5.76e23（Chinchilla 论文的 70B 模型训练算力），按原文公式得 N = 20 × 7.6e11 = **1.5e13 = 15 万亿参数**，荒谬。

**正确写法**：
```
C ≈ 6ND，且最优时 D = 20N
⟹ C = 120N²  ⟹  N_opt ≈ √(C/120) ≈ 0.091·C^0.5
                 D_opt = 20·N_opt ≈ 1.83·C^0.5
```
代入 C = 5.76e23 → N ≈ 6.9e10 = **69B**，与论文的 70B 吻合。

**同一题里「10× 算力 → 各扩 3 倍」是对的**（10^0.5 = 3.16），说明作者懂指数、只是常数搬错。改这一行即可。

**附带建议**：同题的「涌现能力」段落现在宜加一句限定——2023 年 Schaeffer 等人的 *Are Emergent Abilities a Mirage?* 指出部分「涌现」是评测指标不连续造成的假象。面试里主动提这个反而是加分项。

#### ✅ P0-3 时效脱节：MCP 章节落后一个规范版本

**位置**：第 10 章整章，尤其第 1 题（L20038）、第 6 题（L20362）

**问题**：题库对齐的是 **2025-11-25** 版规范（这也是 Spring AI 2.0 随附 MCP Java SDK 2.0.0 所实现的版本，所以本身没错）。但 **2026-07-28 版**已经发布，是 MCP 发布以来最大的一次改动，题库完全没有覆盖。

| 变化 | 2025-11-25（题库现状） | 2026-07-28（当前规范） |
|---|---|---|
| 会话 | 有 `initialize` 握手 + `Mcp-Session-Id` | **全部移除，协议无状态** |
| 版本协商 | 握手时协商一次 | 每个请求在 `_meta` 里带 `protocolVersion` |
| 能力发现 | `initialize` 返回 capabilities | 新增必实现的 **`server/discover`** RPC |
| 服务端反向请求 | `sampling/createMessage`、`elicitation/create`、`roots/list` | **MRTR**：返回 `InputRequiredResult`，客户端带答案重试原请求 |
| Sampling / Roots | 核心原语 | **已 deprecated**（最早 2027-07 移除） |
| SSE 断线续传 | `Last-Event-ID` 可恢复 | **移除**，断流即丢请求，必须重发 |
| 列表缓存 | 无 | `ttlMs` + `cacheScope` 成为必需字段 |

**影响的具体题目**：
- **第 1 题**把 `Sampling` 列为核心原语并说「Server 可以反向请求 Client 调用 LLM」→ 在新版里这是 **deprecated** 的路径，正确答法是 MRTR。
- **第 1 题追问 1**「Client 如需感知新增能力，需主动再次发起 `tools/list`」→ 新版 list 端点不再 per-connection，且返回 `ttlMs`，客户端按 TTL 缓存即可。
- **第 6 题**「Streamable HTTP 单一端点支持双向流」→ 新版去掉了 session，长连接语义已变。

**修法**：第 10 章加一节「MCP 规范演进（2025-11-25 → 2026-07-28）」，用上表对照。**这是最好的一道加分题**——面试官如果自己没跟，你讲这个就直接拉开差距。

#### ✅ P1-1 ReAct 示例代码丢了结构化消息

**位置**：第 9 章第 2 题「三种框架实现对比 / Spring AI 1.0 实现」，L17465–L17496

**问题**：手写 ReAct 循环时，把 Observation 拼成字符串塞进 `user` 消息：

```java
StringBuilder transcript = new StringBuilder(question);
...
transcript.append("\n[Thought] 需要调用 ").append(toolCall.name())
          .append("\n[Observation] ").append(observation);
...
.user(transcript.toString())   // ← 每轮都当新用户输入重发
```

**为什么是问题**：
1. 丢弃了 `assistant` 消息里的 `tool_calls` 结构，也丢弃了 `tool` 角色的消息。真实 OpenAI / Anthropic 协议要求 `tool_call_id` 严格配对，否则部分厂商直接 400。
2. 每轮重建 Prompt，system 重复计费，且丢失原始对话的角色边界。
3. 模型看到的是「用户告诉我工具返回了什么」，而不是「我调用了工具、拿到了结果」——推理质量会明显下降。

**正确姿势**：维护 `List<Message>`，每轮追加
`AssistantMessage(toolCalls)` → `ToolResponseMessage(id, result)`，用 `ChatClient.prompt(new Prompt(messages))` 续跑。Spring AI 的 `ToolCallingManager` 内部就是这么做的。

> 这一处不影响「背答案」，但**如果面试让你手写伪代码，照这个写会被扣分**。

## 第三部分：学习路线

### 3.1 先定位：你的牌面

**你的优势（别浪费）：**
- **Java + Spring 全家桶**：这是 2026 年最稀缺的组合。Python 出身的人写 Agent 快，但一到「多租户隔离、事务、灰度、限流、审计」就抓瞎——这些正是企业级 Agent 落地的真正门槛。
- **碳管理业务纵深**：Agent 岗最怕「只会调 API，不懂业务」。你有 5 章碳核算知识，这是别人补不来的。
- **已有的题库**：494 道 AI 题的问答储备，面试「知识面」环节已经领先。

**你的短板（要补）：**
- **没手写过 Agent Loop**——会用框架 ≠ 懂循环。面试官一追问「工具连续失败三次怎么办」就露馅。
- **模型层直觉弱**——不知道 temperature 调到 0 为什么还会不稳定、不知道为什么 8K 上下文里塞 20 个工具就开始乱选。
- **没有可量化的项目结果**——题库里 27 题写「准确率 75%→92%」，但那是编的，面试深挖会崩。

**一句话策略**：
> 不要跟算法背景的人拼「懂模型」，要拼「能把 Agent 稳稳跑在生产上」。你的路线应该是 **工程纵深 + 一个真跑通的业务 Agent**。

### 3.2 六阶段路线

#### 阶段 0：对齐认知（1–2 天，不要省）

先搞清一件事：**Agent 不是「会调工具的 ChatBot」**。

| 层次 | 特征 | 你需要达到 |
|---|---|---|
| L1 ChatBot | 一问一答，无状态 | 已有 |
| L2 RAG 应用 | 检索 + 生成，单轮增强 | 已有 |
| L3 Tool Agent | 模型决策调工具，单轮循环 | **本阶段目标** |
| L4 有状态 Agent | 多轮记忆 + 计划 + 纠错 + 中断恢复 | 8 周目标 |
| L5 Agent 平台 | 多 Agent 协作 + 运行时 + 可观测 | 长期 |

**必读两份材料（各 30 分钟）**：
- Anthropic《Building Effective Agents》—— 把 workflow 和 agent 的边界讲透了，面试引用率极高
- HumanLayer《12-Factor Agents》—— 生产级 Agent 的 12 条工程原则，Java 背景的人会非常有共鸣

**验收**：能用自己的话说清「什么时候该用 workflow，什么时候才该上 agent」。这题面试出现频率极高。

#### 阶段 1：打通一条最小链路（第 1 周）

**目标**：跑通「模型 → 工具 → 多轮 → 流式」全链路，每一层都知道发生了什么。

**技术选型**：**Spring AI 2.0**（2026-06-12 GA，Spring Boot 4.1 / Framework 7 / Java 17+）。

> 为什么不是 LangChain4j？因为你的存量是 Spring，Spring AI 的 Advisor 链、自动装配、可观测性跟你的经验完全同构，学习成本最低。LangChain4j 第 4 周再补，用来回答「两个框架怎么选」。

**要做的事**：
1. 建一个 Spring Boot 4.1 + Spring AI 2.0 项目，接 DeepSeek（便宜，`deepseek-flash`）或 Qwen
2. `ChatClient` 跑通同步 + 流式
3. 写 3 个 `@Tool`，其中**必须有一个会抛异常**、一个返回超长文本
4. 加 `MessageChatMemoryAdvisor`，验证多轮记忆
5. 加 `ToolCallingAdvisor`，观察工具循环的日志

**必须搞懂的 5 个问题**（面试原题）：
1. 模型返回 `tool_calls` 后，**谁**执行工具？（答：你的应用，不是模型。这是 Agent 的安全边界）
2. 工具结果以什么角色回到模型？（`tool` 消息，带 `tool_call_id`）
3. 循环什么时候停？（模型不再返回 `tool_calls`）
4. 流式模式下工具调用怎么处理？（先非流式拿到 tool_calls，执行后再流式出最终答案）
5. `ToolCallingAdvisor` 和 `ChatModel` 的分工？（2.0 把循环上浮到 advisor 链，`ChatModel.call()` 只返回原始响应）

**产出**：一个能查数据库、能算数、会流式输出的命令行助手。

#### 阶段 2：手写 Agent Loop（第 2 周）⭐ 分水岭

**这一步是整条路线最重要的。** 不写这一遍，你永远是「框架使用者」。

**任务**：不用 Spring AI 的自动 tool 执行，**用 `ChatModel` 裸接口 + 自己维护 `List<Message>`**，写一个 150 行以内的 ReAct Agent。

**必须覆盖的边界（这是面试深挖的题库）**：

| 场景 | 你要给出的处理 |
|---|---|
| 模型返回不存在的工具名 | 校验白名单，回灌一条错误 tool 消息让它自纠，而不是抛异常终止 |
| 工具参数 JSON 不合法 | 捕获解析异常 → 把错误信息回灌给模型重试（最多 1 次）→ 仍失败则降级 |
| 工具执行超时 / 抛异常 | 回灌 `{"error": "..."}`，**不要**把堆栈直接给模型（会烧 token 且误导） |
| 模型连续 3 次调同一个工具同样参数 | 判定死循环，注入提示「该工具已返回相同结果，请换思路」或直接终止 |
| 工具返回 5 万 token | 截断 + 摘要 + 外置到文件（这就是上下文工程） |
| 循环超过最大步数 | 返回「已尝试 N 步未完成」+ 已收集的信息，让用户决定 |
| 上下文快满 | 触发压缩：保留 system + 最近 3 轮 + 摘要化历史 |

**产出**：`AgentLoop.java`（约 150 行）+ 一份 README 写清上面 7 个边界怎么处理。

> 这份 README 就是你面试时最硬的底牌。面试官问「你怎么处理工具失败」时，你说「我写了七种边界，其中参数不合法会回灌错误让模型自纠一次」——这句话的含金量超过背 100 道题。

#### 阶段 3：RAG 从能用到可信（第 3–4 周）

**你的优势**：题库第 3 章 67 题已经把 RAG 的概念覆盖透了（chunking 专题尤其好，含 ES 混合检索补充）。**缺的是「你的参数是怎么定的」**。

**任务**：
1. 用你自己的碳管理文档（法规 / 因子库 / 报告）建一个知识库，**至少 200 个 chunk**
2. 走完这条升级链，每步记录指标：
   `naive 向量检索` → `+ hybrid（BM25+向量）` → `+ rerank` → `+ query rewrite` → `+ 上下文压缩`
3. **建一个 50 条 gold set**（问题 + 标准答案 + 应该命中的 chunk id），算 `recall@5`、`MRR`、`faithfulness`
4. 每个参数都要有依据：chunk size 为什么是 800？overlap 为什么 15%？top-k 为什么 5？

**面试会问的**（题库第 3 章都有，但要接上你的数字）：
- 「你的 chunk 策略是什么？」→ 答结构感知切分 + 条款不截断，配你的实际文档类型
- 「检索不准怎么排查？」→ 答：先看 recall 还是 precision 掉，recall 掉查切分和 embedding，precision 掉加 rerank
- 「怎么证明优化有效？」→ **掏出 gold set 和前后对比表**

**产出**：一张「5 个阶段 × 3 个指标」的对比表。这张表比任何话术都管用。
