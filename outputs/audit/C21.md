# C21 审校：第二十六章 Docker与Kubernetes深度（42题）+ 第二十七章 CI/CD与DevOps（29题）

### L50296 | 第二十六章1题 | Docker镜像分层原理
- 类型：1
- 严重度：P1
- 原文：「Layer 3：EXPOSE 8080（元数据）」「每层对应Dockerfile中的一条指令」
- 问题：EXPOSE/ENV/CMD/LABEL/WORKDIR 等元数据指令只写入镜像 config，不产生文件系统层，列进分层图会把"层"的概念讲错；"每条指令一层"也不成立（只有产生文件变更的 RUN/COPY/ADD 才成层）
- 建议：分层图只保留 RUN/COPY/ADD 三层，元数据单独标注"不改动镜像层"

### L50317 | 第二十六章1题 | 镜像分层追问（内容寻址）
- 类型：1
- 严重度：P2
- 原文：「overlay2 以内容哈希（chainID）寻址」
- 问题：chainID 不是内容哈希，它 = hash(parent chainID + " " + diffID)，含父链信息；真正按内容寻址的是 diffID/cacheID（层内容摘要）。且构建缓存命中还要看指令字符串与父层 chainID，不是"内容相同就复用缓存"
- 建议：改为"存储层按 diffID 内容寻址去重；chainID 由父链+diffID 级联，构建缓存键还包含指令本身"

### L50349 | 第二十六章2题 | Dockerfile最佳实践
- 类型：1
- 严重度：P1
- 原文：「HEALTHCHECK：K8s健康检查」
- 问题：kubelet 不执行镜像 HEALTHCHECK（docker run 才用），K8s 只有 liveness/readiness/startup 三种 probe；写成"给 K8s 做健康检查"是错误因果
- 建议：改为"HEALTHCHECK 只对 `docker run`/compose 生效，进 K8s 后由三种 probe 接管，二者不要混用"

### L50384 | 第二十六章3题 | 多阶段构建详解
- 类型：5
- 严重度：P1
- 原文：「COPY --from=deps /build /build」
- 问题：`dependency:go-offline` 把依赖下到 `/root/.m2/repository`，不在 `/build`。这条 COPY 只搬了 pom.xml，builder 阶段仍会重新下载全部依赖，"依赖下载单独成阶段"的优化实际失效，与同段"改代码不重下依赖"自相矛盾
- 建议：改用 `COPY --from=deps /root/.m2 /root/.m2`（或 `RUN --mount=type=cache,target=/root/.m2`）

### L50407 | 第二十六章3题 | BuildKit 远程缓存
- 类型：4
- 严重度：P2
- 原文：「docker build --build-arg BUILDKIT_INLINE_CACHE=1 --cache-to=type=registry...」
- 问题：`--cache-to/--cache-from` 属 buildx 语法，普通 `docker build` 不认；`BUILDKIT_INLINE_CACHE=1` 是旧版内联缓存写法，buildx 已用 `--cache-to type=inline,mode=max` 取代
- 建议：统一写成 `docker buildx build --cache-to=type=registry,ref=...,mode=max --cache-from=type=registry,ref=...`

### L50654 | 第二十六章10题 | Ingress与路由
- 类型：2

### L50771 | 第二十六章12题 | HPA 多指标冲突
- 类型：1
- 严重度：P1
- 原文：「CPU 低触发"缩"，queued 高触发"扩"，HPA 在两者间反复横跳」
- 问题：题目前提错误。HPA 每轮对每个指标算一个期望副本数，然后取**最大值**，多指标不会互相抵消、也不会"横跳"；CPU 低只会让 CPU 这一路期望值低，queued 高照样扩。真正的抖动来自指标毛刺与缩容稳定窗，不是"指标冲突"
- 建议：改写为"HPA 取各指标期望副本数的 max，因此 queued 高时必然扩；风险在于 CPU 长期偏低导致缩容后立刻又扩，应靠 stabilizationWindow 与以 queued 为主信号"

### L50781 | 第二十六章12题 | HPA 指标拉取失败
- 类型：1
- 严重度：P2
- 原文：「Adapter 故障导致指标拉取失败时，HPA 通常维持当前副本数（不误缩），部分版本报 unable to fetch metrics 并暂停扩缩」
- 问题：只有**全部**指标都取不到时 HPA 才跳过本轮扩缩；多指标场景下单个自定义指标失败会被丢弃，HPA 继续用 CPU 等剩余指标计算，此时 CPU 低照样会缩容。"不误缩"过于绝对
- 建议：补一句"仅当所有指标均失败才跳过；单指标失败会降级为按其余指标扩缩，故需保留 CPU 兜底并配 FailedGetExternalMetric 告警"

### L50898 | 第二十六章16题 | PV/PVC/StorageClass

### L50948 | 第二十六章17题 | StatefulSet 缩容
- 类型：1
- 严重度：P0

### L51140 | 第二十六章23题 | Pod安全标准

### L51232 | 第二十六章26题 | 故障排查
- 类型：1
- 严重度：P1
- 原文：「JVM 堆 OOM：看 `Exit code 137` + JVM GC 日志/堆 dump」
- 问题：137 = 128+9（SIGKILL），是容器内存超 cgroup limit 被内核杀掉，也就是"容器 OOM"；JVM 自己抛 OutOfMemoryError 通常以 exit 1 退出（或 134 abort）。把 137 归给 JVM 堆 OOM 会让人调错方向（该调 -Xmx 还是调 limit）
- 建议：改为"137 = 容器/节点 OOMKill（调 limits 或降堆外内存）；JVM 堆 OOM 看 exit 1 + hs_err_pid/堆 dump"

### L51398 | 第二十六章30题 | 优雅终止

### L51951 | 第二十七章9题 | 部署策略与回滚
