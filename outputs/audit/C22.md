# C22 审校：第二十八章 计算机网络（35题）+ 第二十九章 操作系统（43题）

## 第二十八章 计算机网络

### L52503 | 第二十八章第2题 | HTTP/1.1 vs 2 vs 3 对比表
- 类型：1
- 严重度：P1
- 原文：「服务器推送 | 无 | 支持 | 支持」
- 问题：HTTP/3 不支持服务器推送——RFC 9114 直接移除了 Server Push 机制（PUSH_PROMISE 帧已删除）。表中把 HTTP/3 标为"支持"是硬错。另 HTTP/2 的推送虽在 RFC 9113 中保留，但 Chrome 106 已移除、主流实现基本废弃，"支持"也属名义支持。
- 建议：改为「服务器推送：无 | 名义支持（已被主流浏览器移除） | 不支持（RFC 9114 已移除）」，正文补一句"push 已是历史特性，别作为选型理由"。

### L52527 | 第二十八章第3题 | TLS 1.2 握手流程
- 类型：4
- 严重度：P1
- 原文：「生成Pre-Master Secret，用服务端公钥加密发送」
- 问题：这是 RSA 静态密钥交换的流程。现代 TLS 1.2 实际默认走 ECDHE（前向安全），Pre-Master 不经公钥加密传输，而是双方用 Server Key Exchange/Client Key Exchange 交换 DH 参数各自算出。全流程还漏了 ChangeCipherSpec/Finished 两步。
- 建议：改写为"ECDHE 场景：Server Hello 后发 Certificate + ServerKeyExchange（DH 参数+签名），客户端回 ClientKeyExchange 传自己的 DH 公钥，双方各自算出 Pre-Master"，并点名 RSA 密钥交换已不推荐。

### L52601 | 第二十八章第6题 | 正向代理 vs 反向代理
- 类型：6
- 严重度：P2
- 原文：「典型场景：VPN翻墙、企业内网代理上网」
- 问题：VPN 不是正向代理（VPN 是三层隧道，代理是应用层转发），举例本身不成立；且面试题库里出现"翻墙"措辞不合场景。
- 建议：换成"公司统一出口代理、爬虫出口 IP 池、客户端访问被墙/被限速资源时的中转"，VPN 单独作为"网络层隧道，与代理不是一个概念"对比说明。

### L52714 | 第二十八章第10题 | TCP 拥塞控制四算法
- 类型：1
- 严重度：P1
- 原文：「慢启动：初始cwnd小，每收到ACK指数增长（cwnd*=2）」
- 问题：慢启动是"每收到一个 ACK，cwnd += 1 MSS"，结果表现为每个 RTT 翻倍，不是"每收到ACK就把 cwnd 乘 2"。按字面理解会把增长速度快算成 RTT 级别而非 ACK 级别，差一个数量级。
- 建议：改为"每收到 1 个 ACK，cwnd 增加 1 个 MSS；整体表现为每个 RTT 翻倍"，并注明初始 cwnd 为 10 MSS（RFC 6928）。

### L52868 | 第二十八章第15题 | Wireshark 解密 HTTPS
- 类型：4
- 严重度：P2
- 原文：「需要导入服务器私钥或在浏览器导出SSLKEYLOGFILE」
- 问题：导入服务器私钥只能解 RSA 密钥交换的会话；ECDHE 下私钥无法推出会话密钥（这正是前向安全的定义），现在线上几乎全是 ECDHE，该说法会误导排查。
- 建议：改为"仅 RSA 密钥交换可用私钥解密；ECDHE 只能靠 SSLKEYLOGFILE 导出会话密钥，或在隔离环境用可导出密钥的测试栈复现"。

### L53012 | 第二十八章第20题 | VPC 子网与 NAT
- 类型：5
- 严重度：P2
- 原文：「应用服务器在公有子网后面挂载NAT网关」
- 问题：公有子网本身就经 IGW 出网，不需要 NAT；NAT 网关是给私有子网做单向出网的。这句把两个拓扑混在一起，后面又说"AI推理服务通过NAT网关访问公网"，读者无法判断应用到底在哪个子网。
- 建议：改为"应用服务器放私有子网，经 NAT 网关出公网调用大模型 API；仅负载均衡/跳板机放公有子网挂 IGW"。

### L53056 | 第二十八章第22题 | TIME_WAIT 过多怎么缓解
- 类型：1
- 严重度：P1
- 原文：「缓解：timewait 复用(tw_reuse)、调低 MSL、用长连接」
- 问题：Linux 的 TIME_WAIT 时长是内核常量 TCP_TIMEWAIT_LEN=60s，没有任何 sysctl 能改 MSL，tcp_fin_timeout 只影响 FIN_WAIT_2。写"调低 MSL"会让人去翻一个不存在的开关。
- 建议：删掉"调低MSL"，换成实际可做的：tcp_tw_reuse（仅出向、需时间戳）、减少主动关闭方（改由客户端关）、长连接/连接池、扩大 ip_local_port_range、加 SO_REUSEPORT 多实例分摊端口。

### L53154 | 第二十八章第28题 | TCP Keepalive 默认参数
- 类型：3
- 严重度：P1
- 原文：「默认 7200s 空闲才发探测、3 次×75s」
- 问题：探测次数默认是 tcp_keepalive_probes=9，不是 3。按 9×75s 算，死连接要 7200+675≈2h11m 才发现，说成 3 次会把总时长算小一半以上。
- 建议：改为"空闲 7200s 后开始探测，间隔 75s、默认 9 次探测，约 2 小时 11 分才判定死亡"。

### L53178 | 第二十八章第30题 | DNS 解析过程
- 类型：1
- 严重度：P2
- 原文：「递归查询：本地→递归解析→根→顶级域→权威，逐级拿到 IP 并缓存」
- 问题：把递归和迭代混为一谈。客户端→本地DNS 是递归；本地DNS→根/顶级/权威 是迭代（每级只回"下一个该问谁"）。
- 建议：拆成两句："客户端到 Local DNS 是递归查询；Local DNS 到根、顶级、权威是迭代查询"，并补 ARP/浏览器缓存命中这条短路路径。

## 第二十九章 操作系统

### L53371 | 第二十九章第4题 | CPU 调度算法与 CFS
- 类型：4
- 严重度：P1
- 原文：「CFS（完全公平调度）：Linux 2.6+默认调度器」
- 问题：CFS 自 Linux 6.6（2023）起已被 EEVDF（Earliest Eligible Virtual Deadline First）取代为默认调度器，现在讲"Linux 默认调度器是 CFS"已过时；vruntime 概念在 EEVDF 里演化为 lag/eligible/deadline。
- 建议：改为"2.6.23–6.5 默认 CFS（vruntime 红黑树）；6.6 起默认 EEVDF，引入 lag 与虚拟截止时间，但仍属公平类调度器"，面试时说明版本差异反而是加分项。

### L53413 | 第二十九章第5题 | Netty 跨平台多路复用
- 类型：1
- 严重度：P1
- 原文：「跨平台注意：macOS不支持SO_REUSEPORT、epoll专属选项」
- 问题：macOS/Darwin 支持 SO_REUSEPORT（nginx 在 macOS 上就用它做多 worker 监听），只是内核分发语义与 Linux 的四元组哈希不同（早期为 last-in-first-out）。把"不支持"当成跨平台差异会写错判断分支。
- 建议：改为"两者都支持 SO_REUSEPORT，但 Linux 内核按四元组哈希均衡、Darwin 语义不同；真正 linux-only 的是 EPOLLEXCLUSIVE、SO_REUSEPORT 的 BPF 选择器等"，并按平台探测而非按"支持/不支持"硬编码。

### L53539 | 第二十九章第10题 | 用户态/内核态切换开销
- 类型：5
- 严重度：P1
- 原文：「每次切换有上下文保存/恢复开销（几十到上百CPU周期）」
- 问题：与本文后面 L53972/L54003 的"数百纳秒到微秒级"自相矛盾。一次 syscall 往返含特权级切换、栈切换、Meltdown/Spectre 缓解（KPTI 页表切换），实测在 0.1~1μs，即数百到数千周期；"几十个周期"是函数调用量级。
- 建议：统一口径为"数十纳秒（纯模式切换）到 0.5~1μs（含 KPTI、参数拷贝）"，删除"几十到上百CPU周期"。

### L53566 | 第二十九章第11题 | 陷入内核的方式
- 类型：1
- 严重度：P2
- 原文：「用户程序通过软中断（int 0x80或syscall指令）进入内核态」
- 问题：int 0x80 是软中断（可屏蔽中断门），而 syscall/sysenter 是专门的快速系统调用指令，不是软中断，它不经过中断描述符表。两者混在一个括号里概念不清。
- 建议：改为"32 位传统用 int 0x80 软中断门进入；x86-64 用 syscall 指令（走 MSR 指定的入口，比中断门快）"，正好可引出"为什么 syscall 比 int 0x80 快"。

### L53587 | 第二十九章第12题 | 页缓存与脏页回写
- 类型：4
- 严重度：P1
- 原文：「由pdflush定期刷脏页到磁盘」
- 问题：pdflush 在 Linux 2.6.32 就被删除了，现由每个块设备的 flusher 内核线程（flush-8:0 之类，bdi_writeback）按 dirty_ratio/dirty_expire_centisecs 回写。
- 建议：改为"由 per-BDI 的 flusher 线程（如 flush-8:0）按 dirty_background_ratio、dirty_expire_centisecs 阈值异步回写"，保留 pdflush 只作为历史名词说明。

### L53653 | 第二十九章第14题 | 分配算法与 GC 碎片
- 类型：1
- 严重度：P2
- 原文：「GC通过压缩消除碎片（Serial/Parallel GC）或使用空闲列表（CMS/G1）」
- 问题：G1 不是空闲列表分配器，它按 region 做复制式回收（疏散/compaction），CMS 才是 free list。把 G1 归到 CMS 一类会把"G1 不做压缩"这个常见误判写进题库。
- 建议：改为"Serial/Parallel 用标记-压缩；CMS 用空闲列表（因此有碎片、需 Full GC 兜底）；G1 按 region 疏散复制，天然无外部碎片"。

### L53678 | 第二十九章第15题 | 磁盘调度与 IO 调度器
- 类型：4
- 严重度：P1
- 原文：「Linux的CFQ/Deadline/NOOP：CFQ 完全公平队列…NOOP 简单FIFO，适合SSD」
- 问题：CFQ 在 Linux 5.0 已被删除，NOOP 在 blk-mq 下基本被 none 取代，现行是 none / mq-deadline / bfq / kyber。而本节 L53683 又说"使用NOOP或CFQ调度器"，与 L53689 追问里的"SSD 上用 none/mq-deadline"自相矛盾。
- 建议：改为"传统：CFQ(≤4.x)/Deadline/NOOP；现代 blk-mq：none、mq-deadline、bfq、kyber。SSD 首选 none（NVMe 多队列无寻道），SATA SSD 可用 mq-deadline"，并删掉 L53683 的 CFQ。

### L53817 | 第二十九章第20题 | NUMA 与 JVM
- 类型：1
- 严重度：P1
- 原文：「G1 GC有`-XX:+UseNUMA`优化：Eden区按NUMA节点分配」
- 问题：-XX:+UseNUMA 只对 Parallel GC 生效（Parallel Scavenge 按 NUMA 节点分区分配）；G1 不支持 NUMA 感知分配，给 G1 加这个参数等于无效参数，容易让人以为已经优化了。
- 建议：改为"NUMA 感知分配由 ParallelGC 支持；G1/ZGC 不做 NUMA 绑定，需靠 numactl/cpuset 绑核+绑内存，或 JVM 侧用 -XX:+UseNUMA（仅 ParallelGC 有效）"。

### L53917 | 第二十九章第25题 | epoll LT/ET 与 Netty
- 类型：5
- 严重度：P0
- 原文：「Netty 默认用 epoll 传输…并采用 LT 模式」 vs「L54126：Netty 用 epoll 的 ET（边沿触发）模式」
- 问题：同一份题库里第25题说 Netty 用 LT、第36题说 Netty 用 ET，直接对立，被追问必穿帮。另"Netty 默认用 epoll 传输"也不准确：Linux 上默认传输是 NIO（JDK epoll），原生 epoll 传输需显式引入 netty-transport-native-epoll 并指定 EpollEventLoopGroup。
- 建议：统一为"Netty 默认 NIO 传输（JDK 的 epoll 封装，LT）；启用原生 epoll 传输时 EpollMode 默认仍是 LT，可显式切 ET（需自行循环读到 EAGAIN）"，两处措辞对齐。

### L53936 | 第二十九章第26题 | 零拷贝省了几次 CPU 拷贝
- 类型：3
- 严重度：P1
- 原文：「零拷贝走 页缓存→socket 缓冲→网卡，省去两次用户态拷贝」
- 问题：数量算错。传统 read+write 是 2 次 CPU 拷贝（内核→用户、用户→socket）；sendfile 仍有 1 次内核内拷贝（页缓存→socket 缓冲），只省 1 次，不是 2 次。只有叠加网卡 SG-DMA（sendfile+DMA gather）才完全不占 CPU。同一错误在 L54108「CPU拷贝省掉」和 L54144「省掉用户态那 2 次 CPU 拷贝」重复出现。
- 建议：统一表述为"传统 4 次拷贝（2 DMA + 2 CPU）→ sendfile 3 次（2 DMA + 1 CPU）→ sendfile+SG-DMA 2 次（全 DMA，真正零 CPU 拷贝）"，并说明 sendfile 顺带把 4 次态切换降到 2 次。

### L53999 | 第二十九章第29题 | 虚拟线程 vs 协程
- 类型：5
- 严重度：P2
- 原文：「遇 synchronized/本地方法会 pin 住载体，仍是 1:N」
- 问题：两处不准。① 映射比写反了：本文 L53288、L53841 都写 M:N，这里写"1:N"，虚拟线程是 M 个虚拟线程映射到 N 个载体线程。② synchronized 导致的 pinning 在 JDK 24（JEP 491）已解除，只有 native 方法/JNI 栈帧仍会 pin，写"JDK21 行为"要标版本。
- 建议：改为"虚拟线程为 M:N 调度；JDK 21 中 synchronized 与 native 栈帧会 pin 载体，JDK 24 起 synchronized 不再 pin（JEP 491）"。

### L54030 | 第二十九章第31题 | 堆栈与逃逸分析
- 类型：1
- 严重度：P2
- 原文：「逃逸分析可把未逃逸对象标量替换到栈」
- 问题：HotSpot 从来不做"栈上分配"，只做标量替换（拆成局部变量进寄存器/栈槽）；对象本身不会整块分配到栈帧。L54038-54040 的追问又反复说"把对象分配在栈"，会把错误结论固化。
- 建议：改为"逃逸分析后做标量替换/锁消除，把对象拆解为标量直接放寄存器或栈槽（HotSpot 无真正的栈上对象分配）"。

### L54155 | 第二十九章第38题 | MESI 与分布式缓存一致性
- 类型：3
- 严重度：P1
- 原文：「这是硬件层、毫秒级、单机多核」
- 问题：量级错了三个数量级——缓存一致性由总线/目录协议在几十到上百纳秒内完成；毫秒级是跨网络 Redis 的量级。且与同题 L54166「纳秒~微秒级」自相矛盾。
- 建议：改为"硬件层、单机多核、纳秒级（~几十 ns 的缓存行失效），由 CPU 硬件强保证"，与 L54166 口径统一。

### L53130 | 第二十八章第27题 | HTTP/3 彻底解决队头阻塞
- 类型：1
- 严重度：P2
- 原文：「3 基于 QUIC(UDP) 彻底解决队头阻塞」
- 问题："彻底"过头。QUIC 只消除了跨流的 TCP 队头阻塞；单条流内部仍是有序的，该流丢包仍会阻塞这条流；并且丢包恢复、连接迁移、0-RTT 都有各自代价。相同"彻底解决"表述在 L52505、L53137 重复。
- 建议：改为"把队头阻塞从连接级降到流级：一条流丢包只阻塞该流，其它流不受影响"，避免用"彻底"这种绝对化措辞。
