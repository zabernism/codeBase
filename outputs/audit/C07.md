# C07 审校报告：第八章 Prompt工程（L16940~L18023，共25题）

### L16970 | 第8章第2题 | 什么是PromptTemplate
- 类型：1
- 严重度：P0 硬错误
- 原文：「`{{industry}}` 由模板引擎做转义，避免用户输入闭合模板或注入额外指令」
- 问题：Spring AI 的 PromptTemplate 只做占位符替换，**不做任何转义或清洗**，变量值原样拼进模板，模板注入防护归零；"模板引擎转义=防注入"是错的。另 Spring AI 默认分隔符是 `{var}`（StTemplateRenderer），不是 `{{var}}`，`{{}}` 是 LangChain4j/Mustache 的写法，与本文件第9题 Spring AI 代码里的 `{industry}` 自相矛盾。
- 建议：改为"渲染只保证结构完整、不保证安全；防注入须在注入前对变量做标签剥离/转义与长度截断"；并统一 Spring AI 用 `{var}`，`{{var}}` 仅用于 LangChain4j 段落。

### L17037 | 第8章第4题 | Few-shot prompting
- 类型：1
- 严重度：P2 质量偏低
- 原文：「CBAM（碳边境调节机制）是欧盟对进口产品碳含量征收的碳关税」
- 问题：CBAM 官方明确不是"碳关税"，而是进口商按嵌入排放购买 CBAM 证书的碳定价机制；且 2026-01-01 起已结束过渡期进入正式实施，"征收碳关税"的定性在 2026 年既不准也过时。作为 Few-shot 示例会把错误口径教给模型。
- 建议：示例改为"CBAM 是欧盟对进口产品嵌入排放要求购买证书的碳边境调节机制，2026 年起正式实施"，并补一句"Few-shot 示例本身必须经过事实校验，示例错误会被模型放大复制"。

### L17058 | 第8章第5题 | Chain-of-Thought
- 类型：4
- 严重度：P1 过时不准
- 原文：「在 Prompt 中引导大模型逐步推理，适用于复杂分析问题」
- 问题：一是 2026 年主力模型（Qwen3 思考模式、o 系列）原生推理，显式"请逐步思考"收益有限、对推理模型甚至有害（官方建议不要额外 CoT 提示）；二是给出的示例是固定 5 步核算流程，本质是流程模板而非 CoT，且碳足迹数值核算靠 CoT 仍会算错，不能作为准确性手段。
- 建议：补"推理模型不需显式 CoT、非推理模型才用"的分层说明；数值核算改为"CoT 只负责拆步骤，实际乘加走代码/工具调用"，并说明该示例属"流程化 Prompt"。

### L17119 | 第8章第7题 | Prompt版本管理
- 类型：6
- 严重度：P2 质量偏低
- 原文：「1.模板存储 2.Git管理 3.A/B测试 4.配置中心」
- 问题：四条只列手段、无取舍，且三处追问都没覆盖 2026 年最关键的"Prompt 与模型版本绑定"：换模型/换版本后同一 Prompt 行为漂移，版本号必须与 model+params 一起记录，否则回滚 Prompt 也复现不出原效果。
- 建议：补一条"版本四元组 = prompt 版本 + 模型名与版本 + temperature/top_p + 工具与检索配置"，并说明模型升级要触发 Prompt 回归。

### L17176 | 第8章第9题 | 结构化输出JSON Mode
- 类型：2
- 严重度：P2 质量偏低
- 原文：「先剥离模型多余说明文字（正则提取首个 `{...}`）再重试一次」
- 问题：本题目给的 schema 本身是嵌套 JSON（references 为数组套对象），用正则"提取首个 `{...}`"在第一个 `}` 处就会截断，必然解析失败；这是被当作兜底方案给出的，实际不可用。
- 建议：改为括号配对扫描/找第一个 `{` 与最后一个 `}` 之间切片，或直接用 Jackson 的 `readTree` 容错模式；重试时把解析异常信息回灌给模型。

### L17375 | 第8章第12题 | Prompt的Token消耗如何优化
- 类型：5
- 严重度：P1 过时不准
- 原文：「如何在不砍内容的前提下做无损压缩」，答「删冗余举例，用结构化短语」
- 问题：追问前提"无损压缩"本身不成立，回答又是"删举例"，正文与答案自相矛盾；另"Prompt Caching 复用 System 前缀，省运行时 Token"表述错误——缓存降的是计费单价与首字延迟，token 数一个不少。
- 建议：把"无损压缩"改为"有损但可验证的压缩：删举例、改写短语后跑评估集确认指标不掉"；缓存表述改为"降低 System 段的计费成本与 TTFT，不减少 token 数"。

### L17404 | 第8章第13题 | 动态Prompt如何构建
- 类型：2
- 严重度：P1 过时不准
- 原文：「`PromptTemplate.from(...).apply(Map.of(...)).getText()`」
- 问题：`from/apply(Map)/getText` 是 LangChain4j 的 `dev.langchain4j.model.input.PromptTemplate`，Spring AI 的 PromptTemplate 没有这三个方法（应为 `PromptTemplate.builder().template(...).build().render(Map)`）；本章语境是 Spring AI，代码直接照抄跑不通，也与第9题 Spring AI 写法不一致。
- 建议：代码块标注框架；Spring AI 版本改用 builder+render，并把两框架的占位符差异（`{}` vs `{{}}`）写成对照表。

### L17500 | 第8章第16题 | DSPy
- 类型：1
- 严重度：P2 质量偏低
- 原文：「Optimizer：自动调整……」「Teleprompter：DSPy的优化器」
- 问题：Teleprompter 是 DSPy 2.5 之前的旧名，官方已统一改称 Optimizer，两条并列等于把同一概念写两遍，读者会以为 Teleprompter 是 Optimizer 的子类。代码也不可直接运行：MIPROv2 必须显式给 `auto` 或 `num_trials`，且 Retrieve 需先 `dspy.configure(lm=..., rm=...)`。
- 建议：合并为一条并注明"旧称 Teleprompter，2.5 起改名 Optimizer"；代码补 `auto="light"` 与 configure 的 rm 配置。

### L17562 | 第8章第17题 | APE
- 类型：1
- 严重度：P1 过时不准
- 原文：「基于梯度的Prompt优化（Oprompt/Soft Prompt）……通过反向传播优化软Token」
- 问题：OPRO（Optimization by PROmpting）恰恰**不是**梯度方法，它是用 LLM 当优化器、把历史"提示-得分"喂进元提示迭代生成新提示，属于黑盒搜索，API 模型完全可用；把它归到"仅白盒可微模型"一节是概念讲反，会让候选人误以为 OPRO 用不了闭源模型。
- 建议：把 OPRO 移到"基于搜索/LLM 自优化"一类，梯度类只保留 Soft Prompt / Prompt Tuning，并注明 OPRO 正是 API 模型的常用方案。

### L17598 | 第8章第18题 | Meta-Prompting
- 类型：6
- 严重度：P2 质量偏低
- 原文：「Meta-Prompting是用高层Prompt指导LLM生成低层任务Prompt的技术」
- 问题：这是"LLM 生成 Prompt"（与第17题 APE 高度重合），而 Meta-Prompting 原始工作指的是一个 meta 模型统筹调度多个专家实例、汇总产出答案，重点在"编排"不在"写 Prompt"；本题既偏离定义又与 17/19 题内容重复，凑数感明显。
- 建议：要么改名为"用 LLM 生成/改写 Prompt（与 APE 的关系）"，要么按原义改成"meta 模型分工+汇总"的编排模式，并与 APE 明确边界。

### L17668 | 第8章第19题 | 角色扮演Prompt设计技巧
- 类型：3
- 严重度：P0 硬错误
- 原文：「钢铁行业(高炉工艺)CO2排放因子为0.85 tCO2e/t钢[来源:EPA GHG Factor 2024, Table 3.1]」
- 问题：数值与来源双双不成立。高炉-转炉长流程吨粗钢排放约 1.9~2.3 tCO2（worldsteel 口径 ~1.9），0.85 量级更接近电炉/短流程或某类二次材；EPA 的 GHG Emission Factors Hub 只覆盖燃料燃烧与电网，没有"钢铁产品排放因子 Table 3.1"。这个假引用还被复用到 L17692（CoVe 验证问题）和 L17766（单位一致性示例），会形成系统性错误示范。
- 建议：换成可溯源数值（如 worldsteel LCI 2023 长流程 ~1.9 tCO2/t 粗钢，并注明边界），来源写清报告名+年份；同时把该示例标为"示例数值，需以检索结果为准"。

### L17798 | 第8章第22题 | Long Context Prompt优化
- 类型：5
- 严重度：P1 过时不准
- 原文：「Top-3放开头，Top-1放结尾，其余放中间」
- 问题：Top-1 是 Top-3 的子集，同一 chunk 不可能既在开头又在结尾；按字面实现会把 rank-1 片段注入两次或逻辑打架，与下一行"中等相关放中间"也接不上。
- 建议：改为"rank-1 放**结尾**（紧邻问题），rank-2/3 放开头，rank-4 及以后放中间"，并说明首尾各留一段、中间允许截断。

### L17817 | 第8章第22题 | Long Context Prompt优化
- 类型：4
- 严重度：P1 过时不准
- 原文：「通义千问2使用RoPE+动态NTK扩展，128K上下文位置编码衰减较小」
- 问题：Qwen2/Qwen2.5 的长上下文扩展用的是 DCA + YaRN（4K→128K），"动态 NTK"是 Qwen1.5/Llama 时代的做法，张冠李戴；且 2026 年主力已是 Qwen3 系列，128K 也不是卖点，"衰减较小"更与本题自己承认的 Lost in the Middle 冲突。
- 建议：改为"Qwen2.5/Qwen3 通过 YaRN 扩展到 128K，但长上下文仍需重排+精检，不能假设位置编码能解决中段丢失"。

### L17979 | 第8章第25题 | Prompt安全审计
- 类型：2
- 严重度：P1 过时不准
- 原文：「public class PromptSecurityAdvisor implements CallAdvisor { … @Override public String getOrder() … }」
- 问题：Spring AI 的 `CallAdvisor` 除 `adviseCall` 外还必须实现 `String getName()`（Advisor 接口成员），只写 `getOrder()` 编译不过；第24题的 `UserProfileAdvisor` 则两个都没实现。作为可直接抄的代码示例，这是硬伤。
- 建议：两处都补 `getName()`（如 `return "promptSecurityAdvisor";`）与 `getOrder()`，并注明 order 值越小越先执行，安全 Advisor 应 order 最小。
