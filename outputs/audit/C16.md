# C16 审校结果（第十九章 MySQL数据库深度，L40015-L41889，共52题）

### L40162 | 第19章5题 | EXPLAIN执行计划详解
- 类型：1
- 严重度：P1
- 原文：「index：全索引扫描（扫描整棵索引树但无需回表）」
- 问题：type=index 只表示走全索引扫描，是否回表取决于是否覆盖索引；非覆盖时仍要逐行回表，把"无需回表"写进定义会让人误判 type=index 为好事。
- 建议：改为"全索引扫描（扫描整棵索引树；覆盖时可免回表，否则仍需回表）"，并提示 type=index 常是缺合适索引的信号。

### L40187 | 第19章5题 | EXPLAIN优化案例
- 类型：1
- 严重度：P1
- 原文：「建立联合索引(org_id, report_date, emission_amount)，EXPLAIN变为type=range…Extra=Using index，2秒→50毫秒」
- 问题：report_date 是范围条件，索引在 report_date 之后已无序，ORDER BY emission_amount DESC 无法被该索引满足，仍会出现 Using filesort；且 SELECT 列不全在索引内时 Extra 也不会是 Using index。结论"消除排序"不成立。
- 建议：改为 (org_id, emission_amount, report_date) 之类让排序列紧跟等值列，或明确说明需保留 filesort、只优化了过滤与覆盖。

### L40127 | 第19章4题 | 最左前缀原则
- 类型：5
- 严重度：P2
- 原文：「…违背最左前缀，需要全表扫描。解决方案：…或者使用索引条件下推（ICP）在扫描org_id索引时在存储引擎层过滤」
- 问题：同段先说必须全表扫描，又说靠 ICP 兜底；跳过最左列时索引无法 seek，只能 type=index 全索引扫描，ICP 对全索引扫描不生效，前后矛盾且会误导读者以为 ICP 能救。
- 建议：删掉 ICP 兜底说法，只保留"另建 (report_year, emission_type) 索引"或"调整索引顺序/用覆盖索引"。

### L40134 | 第19章4题追问1 | 生成列/函数索引
- 类型：1
- 严重度：P1
- 原文：「对 report_year 建生成列或函数索引 INDEX((YEAR(report_year)))，比 (report_year,emission_type) 更省空间」
- 问题：report_year 本身就是年份列，YEAR(report_year) 无意义（若真是 YEAR 类型还会报无意义结果）；且只索引函数值无法覆盖 emission_type 的过滤，不能替代 (report_year, emission_type)。
- 建议：删除该例；改用 (report_year, emission_type) 或对真正的函数列（如 created_at 的月份）举例，并说明函数索引不能替代多列前缀。

### L40268 | 第19章7题 | ICP 适用条件
- 类型：1
- 严重度：P1
- 原文：「联合索引的最左前缀可以不满足——即使WHERE条件跳过最左列，只要后续列在索引中，ICP仍可在索引层过滤」
- 问题：MySQL 官方 ICP 仅适用于 range/ref/eq_ref/ref_or_null 访问方式；跳过最左列只能退化为 type=index 全索引扫描，该访问类型不启用 ICP。此说法还与本章第4题 L40117 的表述直接冲突。
- 建议：改为"ICP 不能弥补最左前缀缺失；跳过最左列只能走全索引扫描，需另建索引"。

### L40275 | 第19章7题 | ICP 场景案例
- 类型：1
- 严重度：P1
- 原文：「WHERE org_id=? AND emission_type LIKE '能源%' AND status='已审核'…ICP让存储引擎在索引层就过滤掉emission_type不匹配的记录」
- 问题：emission_type 的前缀 LIKE 属于索引范围访问条件本身（range），不是 ICP 下推；status 不在索引中无法下推。本例实际没有可下推条件，"ICP 把回表从10万降到几百"属虚构效果。
- 建议：改成真正可下推的形态，如索引 (org_id, emission_type, emission_time)，WHERE org_id=? AND emission_type=? AND emission_time BETWEEN …，说明 emission_time 作为索引列但非前缀条件被下推。

### L40388-L40392 | 第19章10题 | 半连接优化
- 类型：1
- 严重度：P1
- 原文：「MySQL实现了五种半连接策略：…5. Materialization Scan：物化后扫描而非查找」
- 问题：MySQL 五种半连接策略是 Table Pullout、Duplicate Weedout、FirstMatch、LooseScan、Materialize；"Materialization Scan" 不是策略名（materialize-lookup/materialize-scan 只是 materialization 的执行形态）。
- 建议：把第5项改为 Table Pullout（表拉出），并简述"子查询表可合并到外层时直接拉出"。

### L40401 | 第19章10题 | 子查询改写案例
- 类型：5
- 严重度：P1
- 原文：「原相关子查询每行都执行一次，5万组织需要5万次子查询」
- 问题：示例 SQL 是 `org_id IN (SELECT org_id FROM emission …)`，这是非相关子查询，只会执行一次（可物化），不存在"每行执行一次/5万次"。案例与结论自相矛盾，10秒→200ms 的归因不成立。
- 建议：要么把示例换成真正的相关子查询 `WHERE EXISTS (SELECT 1 FROM emission e WHERE e.org_id=o.org_id AND …)`，要么去掉"相关子查询逐行执行"的描述。

### L40435 | 第19章11题 | 分页优化

### L40567 | 第19章14题追问1 | 间隙锁范围描述

### L40600 | 第19章15题 | 死锁预防策略
- 类型：1
- 严重度：P1
- 原文：「合理设计索引，避免全表扫描导致锁升级」
- 问题：InnoDB 没有锁升级（lock escalation）机制，这是 SQL Server 的概念。InnoDB 全表扫描时的表现是"扫描到的每一行都加锁"，锁数量暴涨，而非升级为表锁（本章 L41211 自己也写了"InnoDB 不会主动将行锁升级为表锁"，前后矛盾）。
- 建议：改为"避免全表扫描导致扫描到的所有行/间隙都被加锁，锁数量与冲突概率暴涨"。

### L40824 | 第19章20题 | 半同步复制
- 类型：1
- 严重度：P2
- 原文：「半同步复制保证主库故障切换后最多只丢失一个已提交事务」
- 问题：该结论只在"被提升的从库正是收到 ACK 的那个、且未发生超时降级"时成立；若提升的是未收到该事务的从库，或已降级为异步，丢失可以多于一个事务。
- 建议：补前提"在 after_sync 且提升已确认从库的前提下，最多丢最后一个未确认事务；降级期间不保证"。

### L40850 | 第19章21题 | 读写分离强制主库

### L41209 / L41222 | 第19章31题 | 锁兼容矩阵
- 类型：1
- 严重度：P0
- 原文：「关键兼容规则：…S与IX冲突（表级S意味着只读…）」／追问1答：「FOR SHARE 加 S 锁，与写入的 IX 不冲突（IX 只声明意图，S 与 IX 兼容）」
- 问题：两处直接对立。表级兼容矩阵里 S 与 IX 是冲突的（IX 与表级 S/X 都冲突），只有 IS 与 IX 兼容。FOR SHARE 之所以不阻塞 INSERT，是因为它在行上加 S 锁、表上只加 IS 锁，不是因为"S 与 IX 兼容"。按追问的写法，读者会得出表级 S 可与 IX 并存的错误结论。
- 建议：追问改为"FOR SHARE 行级 S 锁 + 表级 IS 锁，IS 与 IX 兼容，故不阻塞；表级 S 与 IX 仍冲突"。同时把正文兼容规则补全（S-S 兼容、X 与所有冲突）。

### L41339 | 第19章35题 | 原子DDL
- 类型：1
- 严重度：P1
- 原文：「通过事务性数据字典与DDL log表（mysql.ddl_log）保证DDL…（原子DDL特性本身不依赖redo log实现）」
- 问题：两个错误。①不存在用户可见的 mysql.ddl_log 表，DD log 是数据字典内部的隐藏结构；②事务性数据字典本身就是 InnoDB 表，原子 DDL 的持久化正是靠 redo log + DD 事务，说"不依赖redo log"是反的。

### L41437 | 第19章38题 | MySQL与NoSQL对比
- 类型：4
- 严重度：P2
- 原文：「MongoDB文档模型灵活、原生水平扩展、事务弱」
- 问题：MongoDB 4.0 起支持多文档 ACID 事务，4.2 起支持分片集群分布式事务，"事务弱"是 3.x 时代的结论，作为选型依据已过时（真实差异是事务粒度/性能开销，而非"没有事务"）。

### L41532 | 第19章41题 | 行溢出
- 类型：4
- 严重度：P1
- 原文：「行溢出：VARCHAR/TEXT过长时行数据只存前768字节+溢出页指针」
- 问题：768 字节前缀是 COMPACT/REDUNDANT 行格式的行为；MySQL 5.7 起默认 DYNAMIC，8.0 也只有 DYNAMIC/COMPRESSED，长字段在行内只留 20 字节溢出页指针，不再保留 768 字节前缀。
- 建议：改为"DYNAMIC 行格式下只存 20 字节指针，整列进溢出页；COMPACT 才保留 768 字节前缀"，并注明 8.0 默认 DYNAMIC。

### L41561 / L41569 | 第19章42题 | 统计信息与自动重算
- 类型：1
- 严重度：P1
- 原文：「生产配置innodb_stats_auto_recalc=ON每天ANALYZE TABLE」
- 问题：innodb_stats_auto_recalc 的触发条件是"表数据变更行数超过约 10%"，不是按天定时；且该参数默认就是 ON，写成"生产配置"像是额外优化项，容易误导。

### L41592 | 第19章43题 | 内部临时表
- 类型：4
- 严重度：P1
- 原文：「内存临时表（MEMORY引擎16MB限制）超限转磁盘临时表（InnoDB）性能远低」
- 问题：MySQL 8.0.13 起内部临时表默认用 TempTable 引擎，内存上限由 temptable_max_ram（默认 1GB）控制，溢出后写磁盘临时文件再转 InnoDB 磁盘临时表；"MEMORY 引擎 16MB"是 5.6/5.7 时代的结论。
- 建议：按 8.0 重写：TempTable + temptable_max_ram/temptable_max_mmap，超限落盘；tmp_table_size/max_heap_table_size 只对 MEMORY 引擎临时表生效。

### L41658 | 第19章45题 | GTID 限制
- 类型：4
- 严重度：P1
- 原文：「限制：不支持CREATE TABLE ... SELECT、不支持同时更新事务和非事务表」
- 问题：MySQL 8.0.21 起已支持 GTID 下的 CREATE TABLE ... SELECT（配合原子 DDL），仍写"不支持"属过时；"同时更新事务表和非事务表"的限制也已在 8.0 随原子 DDL 大幅放宽（仅剩跨引擎原子性提示）。
- 建议：加版本前缀——"8.0.21 之前不支持 CREATE TABLE...SELECT；8.0.21+ 已支持"，非事务引擎的限制注明仅对 MyISAM 等引擎成立。

### L41692 | 第19章46题 | 数据类型误区
- 类型：4
- 严重度：P2
- 原文：「常见误区：VARCHAR存IP(应INT UNSIGNED)」
- 问题：INT UNSIGNED 只能存 IPv4，IPv6 无法存储；且整数存 IP 无法直接用 INET6_ATON/INET6_NTOA 做可读转换。
- 建议：改为"IPv4 可用 INT UNSIGNED，兼容 IPv6 应使用 VARBINARY(16) + INET6_ATON/INET6_NTOA"。

### L41872 / L41874 | 第19章52题 | 主从延迟术语
- 类型：1
- 严重度：P1
- 原文：「用户刚写入立即读从库可能读不到（脏读/读旧）」；标题「如何缓解脏读」
- 问题：脏读（dirty read）指读到其他事务未提交的数据，主从延迟读到的是已提交的旧版本，属于"读旧值/违反读己之写（read-your-writes）"，与隔离级别里的脏读是两回事。全章反复用"脏读"描述主从延迟，概念被污染。
- 建议：标题与正文统一改为"读旧值/读己之写失效"，并在首次出现处注明"这不是隔离级别的脏读"。
