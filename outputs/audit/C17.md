# 第二十章 Redis深度 审校（C17，L41897-L43868，共42题）

### L41906 | 第20章1题 | String内编码与SDS
- 类型：1 事实错误
- 严重度：P0 硬错误
- 原文：「它**支持尾部追加（append）**，但**不支持任意位置修改**……（如再次 SET），就会转成 raw 编码」
- 问题：embstr 是只读编码。Redis 源码里 APPEND/SETRANGE/INCR 等写命令走 dbUnshareStringValue()，遇到 embstr 会先转成 raw 再改，所以 embstr **不支持** APPEND；同样，对已存在的 key 再次 SET 是新建对象、按新长度重新选编码，短值仍是 embstr，并不存在「SET 触发转 raw」。本条与本题追问2「embstr不可修改，一旦发生append/修改会一次性转raw」自相矛盾。
- 建议：改为「embstr 完全只读，任何写命令（APPEND/SETRANGE/INCR）都会先转 raw；SET 是新建对象，长度≤44 仍为 embstr」，并删掉「embstr 支持 append」这一句。

### L41939 | 第20章2题 | Hash内编码与rehash
- 类型：6 内容问题
- 严重度：P2 质量偏低
- 原文：「负载因子>1（无bgsave）或>5（有bgsave）时触发」
- 问题：阈值数值对（dict_force_resize_ratio=5），但说「>5（有bgsave）」不准确：有子进程时是**不允许扩容**（dict_can_resize=0），只有负载因子>5 才强制扩容；>1 的常规扩容在有 bgsave/BGREWRITEAOF 时不会发生。表述反了因果。
- 建议：改为「无子进程时负载因子≥1 即扩容；有 bgsave/AOF 重写子进程时抑制扩容，仅当负载因子>5 才强制扩容」。

### L42000 | 第20章4题 | Set内编码与intset
- 类型：1 事实错误
- 严重度：P2 质量偏低
- 原文：「**listpack**（Redis 7.2+）：替代intset某些场景。」
- 问题：7.2 新增的 listpack 编码是给**元素为字符串**的小集合用的（set-max-listpack-entries 128 / set-max-listpack-value 64），intset 依然承担全整数小集合，listpack 并没有「替代 intset」。本题表格（L43617）里写的「intset / listpack」才是对的，两处不一致。
- 建议：改为「listpack（7.2+）：元素为字符串且数量≤128、单值≤64B 时使用，与 intset 并列，不替代 intset」。

### L42033 | 第20章5题 | ZSet与跳表
- 类型：1 事实错误
- 严重度：P1 过时不准
- 原文：「并发友好（CAS更新指针）」
- 问题：这是 Java ConcurrentSkipListMap 的特性，Redis 跳表跑在单线程里，全部是普通指针赋值，没有任何 CAS/无锁结构。把它列为「跳表 vs 平衡树」的优势会误导（Redis 根本不需要并发安全）。
- 建议：删掉「并发友好（CAS更新指针）」，换成「实现简单、无旋转、范围查询直接沿底层链表走、层高随机无需全局重平衡」。

### L42106 | 第20章7题 | HyperLogLog原理
- 类型：1 事实错误
- 严重度：P2 质量偏低
- 原文：「估算基数=m×2^(调和平均数)，其中m=16384，调和平均数= m / Σ(2^(-M[j]))」
- 问题：公式写错。标准式是 E = α_m · m² / Σ2^(-M[j])，可以写成 α_m · m ·（m/Σ2^-M），是「m 乘调和平均数再乘修正系数 α」，没有 2 的指数。写成 m×2^(调和平均) 量纲都不对。
- 建议：改为「E = α_m · m² / Σ(2^(-M[j]))，小/中/大基数再分别做线性计数、原始估计、偏移修正」。

### L42162 | 第20章8题 | Stream与消费者组
- 类型：2 API错误
- 严重度：P2 质量偏低
- 原文：「XTRIM stream_key MAXLEN 1000限制Stream最大消息数（近似裁剪）」
- 问题：不带 `~` 的 MAXLEN 是**精确裁剪**，会精确删到 1000 条；只有 `XTRIM key MAXLEN ~ 1000` 才是近似裁剪（按 macro node 整块删）。这里把两者说反，也就丢掉了「精确裁剪要逐条释放、可能变慢」这个考点。
- 建议：改为「MAXLEN 精确裁剪；MAXLEN ~ N 近似裁剪（按节点整块丢弃、更快）」。

### L42212 | 第20章9题 | 缓存穿透与布隆过滤器
- 类型：3 数字错误
- 严重度：P1 过时不准
- 原文：「n从百万→千万（×10），同m下误判率约升到原值的近10倍量级（例如从0.01%升到约0.1%或更高）」
- 问题：误判率对 n 是**指数**敏感，不是线性。按 k=13、m=19.2Mbit 实算：n=1e6 时 p=1e-4；n=1e7 时 kn/m≈6.78，p≈(1-e^-6.78)^13≈**98.5%**，过滤器基本失效。「10倍/0.1%」严重低估，会让面试者以为不扩容也能凑合。
- 建议：改为「同 m、k 不变时 n 涨 10 倍，误判率会指数级恶化（本例从 0.01% 直接到 90%+，等于失效），必须按新 n 重算 m≈-n·lnp/(ln2)² 重建」。

### L42387 | 第20章13题 | 主从复制与psync

- 问题：PSYNC 是 **Redis 2.8** 引入的部分重同步；4.0 引入的是 **PSYNC2**（psync2，支持主从角色切换后仍能部分重同步、replid/replid2 双 ID）。把 PSYNC 标成 4.0+ 是版本硬错。

### L42429 | 第20章14题 | Sentinel领导者选举
- 类型：1 事实错误
- 严重度：P2 质量偏低
- 原文：「Sentinel之间通过Raft算法选举一个领导者Sentinel执行故障转移」
- 问题：Sentinel 用的是自己实现的「基于 epoch 的投票选举」（类似 Raft 但**不是** Raft，没有日志复制、没有 term 日志匹配），官方文档只说是 "a leader election" 。同一句里的 Cluster 故障转移（L42476）也被写成 Raft，属于同一个以讹传讹。

### L42476 | 第20章15题 | Cluster故障转移
- 类型：1 事实错误
- 严重度：P1 过时不准
- 原文：「从节点通过Raft算法选举升为主节点（slave-priority最高的优先）」
- 问题：两处都错。①选举不是 Raft，是 gossip + epoch 投票；②Cluster 选主排序**只看复制 offset（数据最新者优先）**，`replica-priority` 仅用于「=0 则永不升主」的排除，不参与排序。「priority 最高的优先」是 **Sentinel** 的规则，被错搬到 Cluster。
- 建议：改为「从节点发起 FAILOVER_AUTH_REQUEST，主节点按 epoch 投票、过半即升主；候选排序以 replication offset 最大（数据最新）优先，replica-priority=0 的从节点不参选」。

### L42608 | 第20章18题 | LFU淘汰实现
- 类型：1 事实错误
- 严重度：P2 质量偏低
- 原文：「计数器基于对数计数：counter = max(counter + 1, log2(log2(counter)) + 1)」
- 问题：这个式子不是 Redis 的实现。真实逻辑是**概率自增**：`p = 1/((counter-LFU_INIT_VAL)*lfu-log-factor + 1)`，取随机数 <p 才 +1，counter 上限 255（LFU_INIT_VAL=5）。所以「counter=max(counter+1, ...)」既不存在，也与「对数增长」的描述对不上；真正让 counter 涨得慢的是概率而不是这个 max 公式。
- 建议：写清「16bit 计数器初值 5，按 1/((counter-5)*log_factor+1) 的概率自增，饱和 255；8bit 记录衰减时间，每 lfu-decay-time 分钟减 1」。

### L43097 | 第20章27题 | 过期通知时机

### L43662 | 第20章37题 | Cache Aside与读写模式
- 类型：1 事实错误
- 严重度：P2 质量偏低
- 原文：「Spring Boot 3的@Cacheable实现Read Through，@CachePut实现Write Through」
- 问题：@Cacheable 是**Cache Aside（旁路）**语义——缓存没命中时是**业务方法**自己去查库，缓存层并不负责加载；Read/Write Through 要求缓存层直接代理 DB（应用只与缓存交互，缓存自己回源/回写）。同理 @CachePut 是"每次调用都刷新缓存"，属于旁路写，不是 Write Through。这是 Spring 缓存最常见的概念混淆。
- 建议：改为「@Cacheable/@CachePut/@CacheEvict 都是 Cache Aside 的注解化封装；Read/Write Through 需要 Spring Cache 之外的抽象（如 JPA 二级缓存、Redis 作为 SoR 的封装层）」。

### L43865 | 第20章42题 | 同分排序设计
- 类型：3 数字错误
- 严重度：P2 质量偏低
- 原文：「score 设计为「分数*1e13 + (MAXTIME - 时间)」，同分时新纪录排前」
- 问题：两处错。①方向反了：同样分数下，时间越新 → (MAXTIME - t) 越小 → score 越小 → 在 ZREVRANGE（降序）里排**越后**，实际效果是"老纪录排前"。要新纪录排前应该用 `+ 时间`（或 `MAXTIME - t` 配 ZRANGE 升序）。②精度坑：Redis score 是 double，53 位尾数约 9e15，分数×1e13 后只要原分数 >900 就超精度，同分会被四舍五入合并；且 score 带小数时低位直接被吃掉。
- 建议：改为「score = 分数 * 1e6 + (MAXTIME - 时间戳秒)，并把分数限制在较小量级（或整数化）；同分要新纪录优先则加 `+ 时间`，并注意 double 精度上限」。
