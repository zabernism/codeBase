## 第十六章 JVM与GC深度调优

### L27626 | 第16章1题 | JMM三大特性
- 类型：5 逻辑矛盾
- 严重度：P2
- 原文：「long/double 在 32 位可能非原子，但 JDK 5 后已强制原子」
- 问题：与本题追问1的答案自相矛盾。追问1明确写"JLS 允许此例外，仅规范层面保留例外表述"，即规范从未强制非 volatile 的 long/double 原子；正文却说"JDK 5 后已强制原子"。JSR-133 强化的只是 volatile long/double 的单次原子性，普通 long 的 word tearing 在 JLS §17.7 至今仍被允许。
- 建议：改为"非 volatile 的 long/double 在规范层面仍允许拆分为两次 32 位写（§17.7），只是 HotSpot 在 64 位平台实现上不出现；volatile 修饰后 JSR-133 强制原子"。

### L27645 | 第16章2题 | happens-before 规则
- 类型：6 内容问题
- 严重度：P2
- 原文：「happens-before 八大规则…④ 线程启动/终止规则」
- 问题：编号只有 7 条却称"八大规则"。JLS §17.4.5 实际是 8 条（程序顺序、监视器锁、volatile、线程启动、线程终止、中断、终结器、传递性），本条把"线程启动"和"线程终止"合并为 ④，条数与标题不符，面试时容易被追问"第八条是哪个"。
- 建议：把 ④ 拆成"线程启动规则"和"线程终止规则"两条，补足 8 条后再编号。

### L27671 | 第16章3题 | volatile 底层原理
- 类型：1 事实错误
- 严重度：P1
- 原文：「写操作后插入 StoreStore + StoreLoad 屏障、读操作前插入 LoadLoad + LoadStore 屏障」
- 问题：屏障插入位置写反了。JMM Cookbook 的定义是：volatile 写之前插 StoreStore、写之后插 StoreLoad；volatile 读之后插 LoadLoad 和 LoadStore（都在读之后，不是读之前）。按原文描述，StoreStore 会被放到 volatile 写之后，失去"保证前面普通写先刷出"的意义。
- 建议：改为"volatile 写：StoreStore 在其前、StoreLoad 在其后；volatile 读：LoadLoad 与 LoadStore 均在其后"。

### L27906 | 第16章14题 | Shenandoah 与 ZGC
- 类型：5 逻辑矛盾
- 严重度：P2
- 原文：「易错点：…忽略 Shenandoah 每对象 8 字节转发指针开销」
- 问题：正文与追问1已两次强调"JDK 13 起废弃 Brooks 指针、不再有每对象额外开销"，易错点却仍把 8 字节开销当作现状提醒，前后冲突。读者会以为现代 Shenandoah 仍有该开销。
- 建议：易错点改为"误以为现代 Shenandoah 仍用 Brooks 指针（该指针仅存在于 JDK 12，JDK 13 起改为 load-reference barrier）"。

### L27964 | 第16章17题 | 双亲委派
- 类型：4 过时
- 严重度：P2
- 原文：「自顶向下（Bootstrap→Extension→Application）」
- 问题：Extension ClassLoader 是 JDK 8 及以前的类加载器；JDK 9 起已被 Platform ClassLoader 取代（sun.misc.Launcher$ExtClassLoader → PlatformClassLoader），委派链变为 Bootstrap→Platform→App。全章面向现代 JDK，此处未标注版本差异。
- 建议：改为"JDK 9+：Bootstrap→Platform→Application；JDK 8 及以前第三层是 Extension ClassLoader"。

### L27995 | 第16章18题 | JVM 调优实战
- 类型：4 过时
- 严重度：P1
- 原文：「ZGC 分代 JDK 21 才成熟」
- 问题：分代 ZGC（JEP 439）在 JDK 21 是**实验性**特性，需 `-XX:+UnlockExperimentalVMOptions -XX:+UseZGC -XX:+ZGenerational` 才能启用，并非"成熟可用"；JEP 474 在 JDK 23 才把分代 ZGC 转为默认（非实验）。按原文在 JDK 21 直接给 `-XX:+ZGenerational` 会启动失败。
- 建议：改为"分代 ZGC JDK 21 为实验特性（需 UnlockExperimentalVMOptions），JDK 23 起成为 ZGC 默认模式；JDK 21 生产建议仍用非分代 ZGC"。

## 第十七章 Spring全家桶深度（1-10题）

### L28027 | 第17章1题 | Spring Boot自动装配原理
- 类型：6 内容问题
- 严重度：P2
- 原文：「3.x 还引入了 AutoConfiguration.imports 的分层加载机制，支持测试时按需加载子集」
- 问题：Spring Boot 3.x 并不存在 imports 文件的"分层加载机制"。AutoConfiguration.imports 只是平铺的全限定类名列表，没有层级/分片概念；按需加载子集是 `@ImportAutoConfiguration`（测试切片如 @WebMvcTest 用它指定）提供的，与 imports 文件格式无关。属于臆造特性。
- 建议：删掉该句；如要讲测试切片，改成"测试切片通过 @ImportAutoConfiguration + @OverrideAutoConfiguration 只导入部分自动配置类，与 imports 文件格式无关"。

### L28037 | 第17章1题追问1 | 自动配置顺序与条件过滤
- 类型：1 事实错误
- 严重度：P2
- 原文：「B 声明 after A 只保证 B 的 matches 在 A 之后执行，条件结果互不影响」
- 问题："条件结果互不影响"与 before/after 的存在理由矛盾——@ConditionalOnBean 正是依赖前一个配置类先注册 BeanDefinition 才能命中，这也是 Spring 提供 before/after 排序的核心原因之一。若条件互不影响，顺序声明就只剩日志顺序意义。
- 建议：改为"AutoConfigurationSorter 先排序、再按序评估；OnClass 类条件互不影响，但 OnBean/OnSingleCandidate 依赖前置类已注册，因此顺序会实质影响条件结果"。

### L28081 | 第17章2题追问1 | @Conditional 与远程配置中心
- 类型：1 事实错误
- 严重度：P0
- 原文：「matches 在 Bean 定义注册阶段执行，早于 Nacos 等配置中心 PropertySource 注入时机」
- 问题：结论错误。配置中心的 PropertySource 在 Environment 准备阶段就已就位——Spring Cloud 2020+ 通过 `spring.config.import=nacos:` 走 ConfigData API 在 prepareEnvironment 阶段加载（老版本走 bootstrap context），而 @Conditional 评估发生在 refresh() 的 invokeBeanFactoryPostProcessors 阶段，明显更晚。因此 @ConditionalOnProperty 能读到 Nacos 配置，这是 Spring Cloud 的常规用法。该答案会把人教成"开关必须放本地配置文件"。
- 建议：改为"@Conditional 能读到已加载进 Environment 的远程配置（ConfigData/bootstrap 阶段早于 BeanDefinition 注册）；真正拿不到的是**运行时热更新**的值，条件只在启动时评估一次"。

### L28099 | 第17章3题 | 自定义 Starter
- 类型：2 API/版本错误
- 严重度：P1
- 原文：「Spring Boot 3.x 推荐使用构造器绑定（@ConstructorBinding）」
- 问题：3.x 起单构造器的 @ConfigurationProperties 自动走构造器绑定，**不再需要也不推荐**加 @ConstructorBinding；该注解从 3.0 起只用于"多构造器需指定其一"的场景（且不能再标在构造器上，需标在类上）。原文示例的 record 也没加该注解，正文与示例不一致。
- 建议：改为"3.x 单构造器自动构造器绑定，无需 @ConstructorBinding；仅多构造器时在类上标注以指定"。

### L28138 | 第17章3题追问1 | Starter 默认值
- 类型：5 逻辑矛盾
- 严重度：P2
- 原文：「只要 enabled 默认 true 且类在 classpath，@ConditionalOnMissingBean 就建出可用 Bean」
- 问题：与本题示例代码冲突。示例 record 里 `boolean enabled` 未配置时取原始类型默认值 false，且 @Bean 上明确有 `@ConditionalOnProperty(havingValue="true")`，未配置时 Bean 根本不会创建。答案的"默认 true → 静默可用"结论不成立，等于在错误前提上给改进建议。
- 建议：先区分两种写法：若用 @ConditionalOnProperty(havingValue="true")，未配置即不装配（无静默问题）；只有用 @ConditionalOnMissingBean 且属性类自带 `enabled=true` 默认值时才存在静默可用，应把结论限定到后一种写法。

### L28199 | 第17章5题追问1 | 抽接口后代理策略是否变化
- 类型：5 逻辑矛盾
- 严重度：P1
- 原文：「若未强制且该 Bean 实现了接口，Spring AOP 仍可能走 JDK 动态代理（取决于配置）」
- 问题：与本题正文自相矛盾。正文已说明 Spring Boot 2.x 起 `spring.aop.proxy-target-class` 默认 true（AopAutoConfiguration 中 matchIfMissing=true，走 CglibAutoProxyConfiguration），此时抽接口不会切换成 JDK 代理。答案给"可能变"会让读者误以为默认行为是 JDK 代理。
- 建议：改为"Boot 2.x/3.x 默认 proxyTargetClass=true，抽接口仍走 CGLIB，行为不变；只有显式配成 false 或纯 Spring Framework（非 Boot）环境才会切 JDK 代理"。

### L28203 | 第17章5题追问2 | CGLIB 代理构造执行次数
- 类型：1 事实错误
- 严重度：P1
- 原文：「会执行两次。CGLIB 代理对象 = 目标类子类实例，构造代理对象前必须先调用父类（目标类）构造器」
- 问题：结论错误且与本条第二个要点自相矛盾（下文又写"Bean 单例只构造一次则预热也只一次"）。Spring 的 CglibAopProxy 实际通过 ObjenesisCglibAopProxy 用 Objenesis 实例化代理，**不调用父类构造器**；即使走普通 Enhancer.create()，父类构造器也只执行一次（构造代理实例那次），不存在"两次"。真正跑两次的是手写 `new Enhancer().create()` 又额外 new 了目标对象这种写法。
- 建议：改为"Spring 用 Objenesis 创建代理实例，目标类构造器不会被代理额外触发一次；但把有副作用的预热写进构造器仍然危险（可能早于依赖就绪、@Lazy 下延迟触发），应移到 @PostConstruct/SmartLifecycle"。

### L28184 | 第17章5题 | JDK 动态代理
- 类型：4 过时
- 严重度：P2
- 原文：「生成的代理类字节码位于 com.sun.proxy 包下」
- 问题：JDK 9 模块化后动态代理类位于 `jdk.proxy1`/`jdk.proxy2` 等动态模块，类名为 `jdk.proxy1.$Proxy0`；`com.sun.proxy.$Proxy0` 是 JDK 8 及以前的形态。且默认不落盘，需 `-Djdk.proxy.ProxyGenerator.saveGeneratedFiles=true` 才可见。
- 建议：注明版本差异：JDK 8 为 com.sun.proxy.$ProxyN，JDK 9+ 为 jdk.proxyN.$ProxyN（动态模块），并说明落盘需开 saveGeneratedFiles。

### L28360 | 第17章7题 | AOP Token 计量
- 类型：2 API/版本错误
- 严重度：P1
- 原文：「meterRegistry.gauge("carbon.ai.cost.usd", tags, cost.doubleValue())」
- 问题：Micrometer 的 `gauge(name, tags, number)` 会**强引用传入的数值对象**并返回一个指向它的 gauge。每次调用都用新的 Double，第二次起返回的是第一次注册的 gauge，读数永远停在首次的值，指标失真；而且这种"每调用一次注册一个 gauge"的写法还会累积注册表条目。按次累加的量应该用 Counter 或 DistributionSummary。
- 建议：改为 `meterRegistry.summary("carbon.ai.cost.usd", tags).record(cost.doubleValue())`，或在 Gauge 上挂一个可变的 AtomicReference/累计器。

### L28300 | 第17章7题 | 成本注解默认值
- 类型：3 数字错误
- 严重度：P2
- 原文：「String costPerToken() default "0.002"; // 美元/Token」
- 问题：0.002 美元/Token 折合 2000 美元/百万 Token，比主流大模型实际单价高出 2–3 个数量级（qwen-max 约 ¥0.02/千 Token 量级）。按此默认值算配额与成本会严重失真，且用 String 承载数值再 Double.parseDouble 也绕过了精度控制。
- 建议：默认值改为按千 Token 计价的合理量级（如 "0.000002" 或直接以 `double costPer1kTokens` 表达），并用 BigDecimal.valueOf 直接构造，避免 Double 中转。

### L28747 | 第17章13题 | DispatcherServlet 流程
- 类型：5 逻辑矛盾
- 严重度：P1
- 原文：「5. HandlerAdapter 适配…调用其 handle 方法执行 Controller 方法 / 6. 拦截器前置处理」
- 问题：步骤顺序颠倒。doDispatch 的真实顺序是 getHandler→applyPreHandle(preHandle)→ha.handle(...)，preHandle 在 HandlerAdapter.handle 之前、也在参数解析之前执行。按原文，拦截器前置处理排在 Controller 执行之后，读者会错误理解 preHandle 能否拦下参数解析/校验失败。
- 建议：把"拦截器 preHandle"挪到第 5 步之前（getHandler 之后、HandlerAdapter.handle 之前），并注明 preHandle 返回 false 时不会进入参数解析与 Controller。

### L28848 | 第17章14题 | 拦截器 ThreadLocal 清理
- 类型：6 内容问题
- 严重度：P1
- 原文：「afterCompletion 里 TenantContext.clear()」，preHandle 中配额不足时 `return false`
- 问题：示例自身有泄漏。preHandle 已经在 28827 行 set 了 TenantContext，随后配额检查失败 `return false`；而 Spring 只对 preHandle 返回 true 的拦截器回调 afterCompletion，此时 TenantContext 不会被清理，线程池复用即串租户——恰好是本题追问1想论证"不会残留"的反例。
- 建议：在 preHandle 的每个 return false 分支里先 TenantContext.clear() 再返回；或把 set 动作放到配额检查通过之后。

## 第十七章 Spring全家桶深度（11-30题）

### L28648 | 第17章11题 | @Transactional 失效示例代码
- 类型：6 内容问题
- 严重度：P2
- 原文：「外层 importCarbonData 标 REQUIRED；内部 self.saveOne 标 REQUIRES_NEW；catch 中 setRollbackOnly 后 throw e」
- 问题：示例的事务语义本身就是错的。外层事务调用 REQUIRES_NEW 内层，内层是独立事务、先提交；外层随后因 setRollbackOnly/抛出而回滚，内层已插入的数据**不会**被撤销，于是"导入抛异常但部分数据已落库"。这段代码被当作"修复方案"展示，会误导读者以为 setRollbackOnly 能兜住内层事务。
- 建议：改用 REQUIRED（加入外层）或把 saveOne 的独立事务改为"收集失败项而不是中途抛异常"；若确需 REQUIRES_NEW 单条提交，必须说明"内层提交不可回滚，外层失败要补偿删除"，不能与 setRollbackOnly 混用。

### L28971 | 第17章15题 | 全局异常处理
- 类型：6 内容问题
- 严重度：P2
- 原文：「@ExceptionHandler(AuthenticationException.class) → 返回 401」
- 问题：@RestControllerAdvice 只处理 DispatcherServlet 内抛出的异常。认证失败发生在 Filter 链（ProviderManager/AuthenticationEntryPoint 层），根本到不了 HandlerExceptionResolver，这个 handler 对"登录凭证错误"实际不生效，真正生效的是 AuthenticationEntryPoint（本库第 17 题也这么写了）。两题口径不一致。
- 建议：注明"仅覆盖 Controller 内抛出的 AuthenticationException；Filter 层认证失败由 AuthenticationEntryPoint 处理"，并让第 15、17 题口径统一。

### L29103 | 第17章16题追问2 | 超大请求体边界
- 类型：1 事实错误
- 严重度：P1
- 原文：「tomcat 有 max-post-size / max-http-form-post-size，超限直接拒绝」
- 问题：`server.tomcat.max-http-form-post-size`（maxPostSize）只在解析 **form 表单**（application/x-www-form-urlencoded、multipart）时生效，对 `application/json` 的请求体不做任何限制，10MB JSON 会被正常读进内存反序列化。原文把它当作 JSON 的兜底防线，结论"不会 OOM"不成立；`spring.servlet.multipart.max-file-size` 同样只对 multipart 生效。
- 建议：补充真正的生效手段：Tomcat 无内置 JSON 体积上限，需自建 Filter 校验 Content-Length/`ContentCachingRequestWrapper` 限流，或网关侧（Nginx client_max_body_size）限制；若用 WebFlux 才有 `spring.codec.max-in-memory-size`。

### L29253 | 第17章18题 | JWT 黑名单异常类型

### L29328 | 第17章19题 | OAuth2 四种模式

### L29437 | 第17章20题 | RBAC 权限注解
- 类型：6 内容问题
- 严重度：P1

### L29628 | 第17章21题 | 事务事件监听
- 类型：5 逻辑矛盾

### L29876 | 第17章23题 | 并行检索编排
